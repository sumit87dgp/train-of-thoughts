1. EXECUTIVE SUMMARY (30-SECOND PITCH)
================================================================================

We built a browser-based SSH terminal (MobaXterm-style) for lab engineers to
connect to Systems Under Test (SUTs) by FQDN. Browsers CANNOT speak SSH
natively, so we introduced a WebSocket-to-SSH gateway: the React UI renders a
terminal with xterm.js, opens a WebSocket to our gateway, and the gateway opens
a paramiko SSH session to the target host and bridges bytes both ways. The REST
API was intentionally NOT used for terminal I/O — long-lived, bidirectional
streams belong on a dedicated service.

================================================================================
2. WHY WE IMPLEMENTED THIS
================================================================================

Need                              | Why WebSocket + gateway
----------------------------------|---------------------------------------------
Interactive shell in browser      | HTTP cannot stream keyboard + live stdout
SSH to arbitrary lab FQDNs        | Browser has no TCP/socket access to port 22
SSO-aligned identity              | Gateway validates same headers as /api/v1/me
Azure production path             | Static SPA + stateful gateway on AKS
Incremental delivery            | UI first, then real SSH, Postgres bookmarks later

Product shape:
  Left   = saved SUT list
  Centre = terminal
  Right  = reserved (future: ADLS artifact register)

4. WHAT IS A WEBSOCKET? (INTERVIEW FUNDAMENTALS)
================================================================================

HTTP                          | WebSocket
------------------------------|------------------------------------------
Client asks, server answers   | Persistent full-duplex channel
Connection ends per request   | Both sides push anytime
Great for REST APIs           | Great for chat, live dashboards, terminals
fetch('/api/...')             | new WebSocket(url) after HTTP Upgrade

Handshake (simplified):
  1. Client sends HTTP with Upgrade: websocket
  2. Server responds 101 Switching Protocols
  3. Same TCP connection carries framed messages (text or binary)

OUR PROTOCOL ON TOP:

Phase      | Frame type   | Payload
-----------|--------------|--------------------------------------------------
Handshake  | Text (JSON)  | Client -> {"action":"connect", fqdn, port, user, pw}
Handshake  | Text (JSON)  | Server -> {"type":"ready"} or {"type":"error",...}
Data       | Text (raw)   | Terminal bytes both directions
Teardown   | Text (JSON)  | Server -> {"type":"closed"} (optional)

We used text frames because xterm output is UTF-8 strings.

6. ISSUES WE HIT AND HOW WE FIXED THEM
================================================================================

ISSUE 1 — WebSocket connection failed (ws://localhost:5173/ws/terminal)
-----------------------------------------------------------------------
Symptom: Console "WebSocket connection failed"
Cause:   Terminal gateway not running on port 8002
Fix:     Start gateway alongside npm run dev:
         fastapi dev src/sppo_data_360_terminal_gateway/main.py --port 8002

ISSUE 2 — WebSocket failed (ws://127.0.0.1:8002) on WSL2
--------------------------------------------------------
Symptom: curl localhost:8002/health OK inside WSL, browser fails
Cause:   Browser on Windows; 127.0.0.1:8002 is Windows loopback, not WSL
Fix:     Vite proxy: ws://localhost:5173/ws/terminal -> WSL :8002
Lesson:  Match where the browser points vs where the process listens

ISSUE 3 — Missing SSH password
------------------------------
Symptom: Auth failures / no way to authenticate
Cause:   Only username collected
Fix:     Password field in toolbar; sent in connect JSON; not persisted

ISSUE 4 — Connection flicker / reconnect loop (IMPORTANT)
---------------------------------------------------------
Symptom: Ubuntu MOTD appears, then "Connecting to..." again; status "Connected"
Cause:   React useEffect in TerminalView depended on session object and
         onSessionEstablished callback. After successful SSH:
           1. onSessionEstablished -> recordSuccessfulConnect -> SUT state update
           2. Parent re-renders -> NEW session object + NEW callback reference
           3. Effect cleanup DISPOSES WebSocket -> effect re-runs -> NEW connection
Fix:     Session snapshot — activeSession state set only on Connect
Fix:     Callback refs (onEstablishedRef) — parent updates don't retrigger effect
Fix:     Effect deps [connected, session] with stable snapshot object

Interview line:
  "Classic React bug: don't put non-memoized objects in effect deps when the
   effect owns long-lived connections like WebSockets."

ISSUE 5 — Double onClose / spurious disconnect
----------------------------------------------
Symptom: Disconnect handler firing twice
Fix:     sessionEnded guard; dispose() sets disposed=true before ws.close()

7. DESIGN PATTERNS & PRINCIPLES
================================================================================

Pattern              | Where                          | Interview phrasing
---------------------|--------------------------------|-------------------------------
Gateway / BFF        | sppo-data-360-terminal-gateway | Shield browser from SSH
Strategy             | attachTerminalSession()        | WS vs demo shell swap
Bridge               | ws_handler._bridge_io          | WS <-> SSH protocols
Adapter              | paramiko, xterm                | Wrap foreign interfaces
Snapshot             | activeSession at Connect       | Stable through re-renders
Ref for callback     | onEstablishedRef               | Avoid effect churn
Disposable resource  | { dispose } from attach*       | useEffect cleanup pattern
Fail-fast validation | Pydantic ConnectMessage        | Reject bad handshake early
Separation of concerns| UI != API != Gateway          | Independent deploy/scale
12-factor config     | .env, VITE_* vs server secrets |

Anti-patterns avoided:
  - SSH passwords in Postgres or localStorage
  - Open WebSocket relay without origin + SSO checks
  - Bolting WebSocket onto stateless REST API

8. SECURITY & PRODUCTION (AZURE)
================================================================================

Production chain (text flow):

  Browser HTTPS
    -> wss:// (same host or trusted subdomain)
    -> Gateway validates Origin
    -> Gateway validates SSO headers
    -> SSH outbound from AKS to lab
    -> Key Vault for gateway keys
    -> TERMINAL_SSH_ALLOW_UNKNOWN_HOSTS=false
    -> Audit log: user, fqdn, connect/disconnect (NOT password)

Topic        | Dev                    | Production
-------------|------------------------|------------------------------------------
Transport    | ws:// + Vite proxy     | wss:// ONLY
SSH host keys| Auto-add OK            | Strict known_hosts
Password     | User per session       | Prefer Key Vault keys
Ingress      | Local ports            | WS enabled, idle timeout 30-120 min,
             |                        | sticky sessions if multi-replica
Network      | WSL port proxy         | AKS -> VNet/peering -> lab firewalls

10. INTERVIEW Q&A
================================================================================

--- ARCHITECTURE ---

Q: Why not SSH directly from the browser?
A: Browsers sandbox JS — no arbitrary TCP to port 22. Need server-side SSH
   plus browser-safe protocol (WebSocket).

Q: Why WebSocket instead of HTTP polling?
A: Polling adds latency, wastes connections, poor for keystroke interactivity.
   WS is full-duplex — standard for web terminals (Codespaces, CloudShell).

Q: Why separate microservice vs WS on existing FastAPI?
A: Different scaling (long-lived connections), ingress timeouts, security
   boundary (outbound SSH). Keeps REST stateless and cacheable.

Q: How does auth work on WebSocket?
A: HTTP Upgrade sends cookies + Origin. Gateway reads SSO proxy headers
   (X-Forwarded-Email) like REST API. Prod rejects unauthenticated upgrades.

Q: Where does the password go?
A: Once in first JSON over established WS; paramiko uses it for that session
   only — not logged, not in DB, not in VITE_*.

--- WEBSOCKETS DEEP DIVE ---

Q: What happens during WebSocket handshake?
A: Client GET with Connection: Upgrade, Upgrade: websocket, Sec-WebSocket-Key.
   Server 101 + Sec-WebSocket-Accept. Connection becomes framed WS protocol.

Q: WebSocket vs SSE?
A: SSE is server->client only. Terminal needs client->server keystrokes.

Q: WebSocket behind load balancer?
A: Enable WS on ingress; increase idle timeout; sticky sessions if per-pod state.

Q: Close code 1006?
A: Abnormal closure — often couldn't connect (nothing listening, TLS, proxy drop).

--- REACT / FRONTEND ---

Q: Why did terminal flicker after connect?
A: useEffect re-ran when session/callback refs changed after recordSuccessfulConnect.
   Fixed with session snapshot + callback refs.

Q: Why xterm.js?
A: Mature emulator — ANSI, cursor, scrollback; VS Code terminal ecosystem.

Q: Terminal resize?
A: ResizeObserver + FitAddon. Future: rows/cols JSON to gateway for resize_pty.

--- BACKEND / SSH ---

Q: Why paramiko?
A: Pure Python SSH; blocking connect/recv in asyncio.to_thread.

Q: How does the bridge work?
A: Two async tasks: SSH->WS and WS->SSH. asyncio.wait(FIRST_COMPLETED).

Q: Slow SSH output?
A: Poll recv with 20ms sleep when empty; don't treat empty as closed until
   exit_status_ready.

--- TRADE-OFFS ---

Q: What's v2?
A: Postgres users/suts/user_suts; bastion; PTY resize; audit; rate limits.

Q: Biggest production risk?
A: Network path AKS -> lab SUTs (firewalls, peering) — not React code.

Q: Password over WebSocket in prod?
A: OK over wss:// with SSO gateway for v1; long-term prefer keys + RBAC on FQDNs.

13. MENTAL MODEL — ONE PARAGRAPH FOR INTERVIEWS
================================================================================

"I built a three-tier flow: React and xterm.js for UX, a dedicated FastAPI
WebSocket gateway that validates SSO and bridges to paramiko SSH, and lab hosts
reached only from the server side. We chose WebSocket because HTTP can't carry
interactive bidirectional terminal I/O. The interesting bugs were operational
— WSL2 localhost routing — and React lifecycle — reconnect loops when parent
state updated after connect. We fixed the latter with immutable session
snapshots and stable effect dependencies. For Azure, the SPA is static; the
gateway needs wss://, ingress WebSocket support, Key Vault keys, and lab
network peering."
